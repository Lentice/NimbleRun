# NR-028 — AppsFolder launch identity and program-like item filter

- Status: `ready`
- Phase: 2
- Depends on: NR-005、NR-006、NR-008、NR-013、NR-019
- Source: `docs/design-spec.md` §2.6、§FR-004、§FR-004a、§FR-005、§FR-006、§FR-010、§FR-013、§10.3、AC-006

## Goal

修掉一個 P0 啟動缺陷，並讓 catalog 預設只列出程式類項目。

`src/catalog/appsfolder_catalog.cpp` 取 AppsFolder 子項目的 Shell parsing name 後**原樣**存入 `AppEntry::launch_identity`，`src/launch/shell_launch.cpp:18` 再把它直接交給 `ShellExecuteExW`。但 AppsFolder 的 parsing name 不是可獨立啟動的字串（design-spec §2.6），使用者按下去只會看到 Windows 的「找不到 …」錯誤對話框。

在開發機上實測列舉全部 313 筆 AppsFolder 項目：

| 交給 `SHCreateItemFromParsingName` 的字串 | 可解析 |
|---|---|
| 目前實作存的 parsing name 原字串 | **39 / 313** |
| `shell:AppsFolder\` ＋ 同一個 parsing name | **313 / 313** |

**即 87%（274 筆）的「Windows app」項目目前按下去必定失敗。** 僥倖能動的 39 筆是 parsing name 恰好等於真實絕對路徑的項目（例：`D:\Program files\Notepad3\Notepad3.exe`）。

同時，`appsfolder_catalog.cpp` 完全沒有任何非 App 過濾，而 `start_menu_catalog.cpp:114-127` 有。所以 `.chm` 說明檔、`.url` 網站捷徑只要以「Windows app」身分出現就會進到清單裡。本 item 把該判準抽成共用純值模組並補到 AppsFolder，同時把黑名單改成白名單。

## 已查證的事實（不必重查）

- `SIGDN_DESKTOPABSOLUTEPARSING` 與 `SIGDN_PARENTRELATIVEPARSING` 在 313 筆 AppsFolder 子項目上**回傳完全相同的字串**（differ=0，兩者皆無失敗）。因此本 item **不需要改取值用的 SIGDN**，只需要在組裝 launch identity 時加前綴。
- 因為取值不變，`stable_id` 的來源字串不變 → **既有 pin 與使用紀錄零遷移**。這是本 item 刻意維持的性質，見 design-spec §10.3。
- parsing name 的三種實際形態：AUMID（`com.squirrel.GitHubDesktop.GitHubDesktop`、`Microsoft.WindowsCalculator_8wekyb3d8bbwe!App`、`Microsoft.AutoGenerated.{96C20C2F-…}`）、Known Folder GUID 相對路徑（`{7C5A40EF-…}\AutoIt3\Au3Info.exe`）、真實絕對路徑。
- **AUMID 含點號，但點號後方不是副檔名。** 天真地「取最後一個點之後」會把 `Microsoft.WindowsCalculator_8wekyb3d8bbwe!App` 判成副檔名 `.windowscalculator_8wekyb3d8bbwe!app`。實測 313 筆中這樣誤判出 200 個以上不存在的「副檔名」。判斷路徑與 AUMID 的可靠依據是**字串是否含反斜線**。
- 開發機上含反斜線那批的實際副檔名分布：`.exe` 102、`.url` 12、`.chm` 10、`.html` 7、`.txt` 7、`.msc` 4、`.pdf` 4、`.rtf` 2、`.bat` 1、`.com` 1。無 `.msi`。
- `start_menu_catalog.cpp:55` 的 `AcceptExtension` 只收 `.lnk`／`.appref-ms`／`.exe`，所以 `.msi` 進不了 Start Menu 來源。使用者自訂資料夾的 `catalog_extensions` 預設也不含 `.msi`。
- `src/settings/settings_store.cpp:289-296` 讀檔時接受**任意**副檔名清單；`settings_editor.cpp:328` 只增減被勾選的那一項，不會清掉使用者手動加入 `settings.ini` 的副檔名。但對話框只有五個寫死的勾選框（`src/resources/NimbleRun.rc:35-39`），**沒有自由輸入欄**，所以加入 `.msi` 這類副檔名目前只能手改 `%LOCALAPPDATA%\NimbleRun\settings.ini`。這是已知限制，本 item 不改。

## Scope

### 1. 新模組 `src/catalog/app_filter.{h,cpp}`

純值，加入既有的 catalog 庫。介面：

```cpp
// True when the target looks like a launchable program rather than a document,
// website, or uninstaller (design-spec §FR-004a). `target` is a Start Menu
// shortcut's resolved target or an AppsFolder item's Shell parsing name.
bool IsProgramLikeTarget(std::wstring_view target);
```

判斷順序（第一個成立者決定結果）：

1. `target` 為空 → `false`。
2. `target` **不含** `\` 也不含 `/` → AUMID，`true`。**在此之前不得做任何副檔名運算。**
3. `target` 是 URL scheme（`scheme://`，`file:`／`FILE:` 除外）→ `false`。
4. 檔名主體（最後一段、去掉最後一個副檔名後）以 `unins` 開頭（大小寫不敏感）→ `false`。
5. 最後一段的副檔名（大小寫不敏感）屬於白名單 `.exe .com .bat .cmd .lnk .appref-ms .msc` → `true`；否則 `false`。無副檔名的路徑 → `false`。

實作上把 `start_menu_catalog.cpp` 現有的 `ToLower`／`FileName`／`FileStem`／`Extension`／`IsUrlTarget` 搬進本模組並由 header 導出必要者，或在本模組內保留私有副本後讓 `start_menu_catalog.cpp` 改用導出版本——**擇一，不得留下兩份**。

`start_menu_catalog.cpp` 的 `LooksLikeNonAppTarget` 刪除，改呼叫 `!IsProgramLikeTarget(...)`。注意語意變動：原本 `link.target` 為空時不做判斷（保留該項目，因為 `.lnk` 路徑本身可啟動），**此行為保留**——`target` 為空時仍不呼叫判準、仍保留項目，不要因為第 1 條規則回傳 `false` 就把它濾掉。`ShortcutIsWeb` 的 web 捷徑判斷（走 PIDL／`SIGDN_URL`）維持原樣，本模組不取代它。

### 2. `src/catalog/appsfolder_catalog.cpp`

`BuildAppsFolderEntry` 內，在既有的 `display_name.empty() || parsing_name.empty()` 檢查之後：

- 新增 `if (!IsProgramLikeTarget(parsing_name)) return false;`（呼叫者維持既有行為：略過該筆並計入 `failed_items`）。若要區分「不可用」與「刻意排除」兩種略過原因，可在 `AppsFolderEnumerateResult` 加一個 `filtered_items` 計數並記入診斷；不強制。
- `out.launch_identity` 改為 `L"shell:AppsFolder\\" + parsing_name`。
- `out.source_path` 維持 `parsing_name`（顯示用，UI 對 AppsFolder 來源顯示的是集中字串 `Windows app`，不顯示此欄）。
- `out.stable_id` 維持 `HashStableId(NormalizePathKey(parsing_name))`，**一個字元都不改**。

`BuildAppsFolderEntry` 已經是可從測試直接呼叫的純函式（不碰 COM），全部新行為都在它裡面，測試打在這裡。

### 3. 不動 `src/launch/shell_launch.cpp`

啟動層不對 `launch_identity` 加工（design-spec §FR-010）。前綴組裝是 catalog 來源的責任。

### 4. 不動 `src/catalog/user_folder_catalog.cpp`

`IsProgramLikeTarget` **不得**套用於使用者自訂資料夾（design-spec §FR-004a 末段）。該來源的把關者是使用者勾選的 `catalog_extensions`；二次過濾會把使用者手動加入 `settings.ini` 的副檔名（例如 `.msi`）無聲擋掉。

### 5. 新設定 `include_windows_apps`

- `src/settings/settings_store.h`：`Settings` 新增 `bool include_windows_apps = true;`（緊接 `hide_after_launch` 之後）。
- `src/settings/settings_store.cpp`：比照 `hide_after_launch` 在預設（L158 附近）、`ParseLine`、序列化（L312 附近）三處各加一行。舊設定檔沒有這個 key 時取預設 `true`（`ParseLine` 未命中即保持 `DefaultSettings()` 的值，不需額外程式碼）。

## Non-goals

- 不做「可啟動性偵測」。曾考慮過對每個項目做離線可啟動性檢查後隱藏失敗者，已否決：`ShellExecute` 前沒有可靠的 dry-run，而且真正的問題是我們存錯了字串，不是項目壞掉——過濾會把修好後其實能開的項目誤殺。
- 不新增「允許非程式項目」設定。FR-004a 無條件生效。
- 不處理安裝檔（`.msi`／`.msix`／`.appx`）：它們目前進不了 Start Menu 與 AppsFolder 來源，需要時使用者可自行在 `settings.ini` 的 `catalog_extensions` 加入，經使用者自訂資料夾進來且不受 FR-004a 過濾。
- 不為 `Extensions to scan` 加自由輸入欄。
- 不改 `stable_id` 產生規則、不改任何持久化格式、不加 migration。
- 不改 dedup（FR-007）。AppsFolder 項目與同名 Start Menu 捷徑仍各自保留，這是 FR-007 第 3 條的既有決定，不在本 item 範圍。
- 不改 `Launcher` group 的任何控制項，不改 `recent_count`（屬 handoff 預留的 NR-027）。
- 不改圖示、搜尋、排名、翻頁、footer。
- 不回頭修改 NR-005／NR-006／NR-008／NR-019 文件。
